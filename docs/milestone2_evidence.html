1. Implementation Scenario & Architecture

To satisfy the client requirements for managing Kubernetes environments, strengthening container security, and improving deployment reliability, we deployed a real-world scenario on a local host:

  • Vulnerable Target (vulnerable-production-app.yaml): Simulates an unhardened payment processing microservice featuring root execution (UID 0), SYS_ADMIN kernel capability, hostPID: true, writable root filesystem, and host socket mounts (/var/run/docker.sock and /).
  • Deterministic Scanner Layer: Aqua Security Trivy and CNCF Kubescape collect ground-truth CVEs and compliance failures.
  • AI Intelligence Layer: K8sGPT and a local Ollama (llama3.2:1b) engine analyze scanner reports, model the exploit chains, and synthesize production YAML patches without cloud data exposure.

3. Local AI Threat Modeling Output (llama3.2:1b via Ollama)

The scanner findings were ingested by our local AI model without transmitting cluster metadata outside the local perimeter. Below is the captured analysis:

Live AI Threat Analysis Log (Extracted from evidence/ai_threat_analysis.txt)
Threat Vector & Exploit Chain:
• KSV-0005 (SYS_ADMIN) + KSV-0006 (/var/run/docker.sock): Grants arbitrary kernel interaction and direct communication with the host container runtime. An adversary achieving code execution inside the container can break out of container namespaces and gain full host node administrative access.
• KSV-0010 (hostPID: true): Leaks host process visibility, allowing attackers to attach debuggers and snoop passwords/tokens from sibling processes.
• KSV-0014 (Writable Filesystem): Enables persistence by letting attackers download malicious binaries and tamper with system libraries.

Mandated Remediations:
1. Strip all capabilities (drop: ["ALL"]) and set privileged: false.
2. Remove hostPath mounts; use in-memory emptyDir for scratch temp directories.
3. Run as non-root (runAsNonRoot: true, UID 10001) with readOnlyRootFilesystem: true.
